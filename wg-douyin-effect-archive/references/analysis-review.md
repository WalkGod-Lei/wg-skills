# 传播原因分析与用户共识流程

## 独立判断

分析位于基本信息之后。先独立推理，不先索取用户意见来代替分析；如果已有用户观点，仍分清自己的证据判断与用户判断。不要写“好看/可爱/易传播”而缺少具体机制。

围绕实际作品选择相关维度，不要求每款填满全部维度：

- 用户使用动机：拍摄、表达、娱乐、情绪或社交需求。
- 使用与投稿的区别：为什么想试、为什么愿意录制发布，效果是否足以成为作品。
- 核心吸引力：美颜、妆感、视觉风格、内容、反差、动作、互动、表演空间、出片稳定性和使用门槛；判断主因/辅因并解释依据，不因之前研究过美颜就断言所有作品都靠美颜。
- 技术贡献：哪些真实模块、参数、素材和节奏可能支持上述体验，不由“层数很多”推断质量高。
- 传播条件：有证据时讨论上线时长、热点、音乐、作者影响力、推广和适用场景。
- 替代解释：高投稿可能受推广/曝光、上线更久等影响；缺少数据时保留这些可能性，不编造后台指标。

每个核心论点尽量闭合：具体特点→用户体验→可能促成的使用/投稿行为→证据与不确定性。将主因、辅因、未知因素区分，而不是无差别罗列。能提出可借鉴原则，但归档任务不授权新特效制作。

## 证据标签与边界

使用这些语义标签：`工程事实`、`官方说明`、`用户提供`、`实际观察`、`分析推断`。重要推断链接对应截图、代码/参数或来源，不用标签装饰没有证据的主张。

单张效果图不能证明某一美颜层的独立贡献；单个投稿量不能证明因果，投稿量不等于独立用户。截图不能推导后台流量、留存或用户画像。用户确认表示认可共同判断，不等于实验证实因果。

投稿量低/未知/尚未发布时，明确“潜在吸引力分析，传播表现尚未验证”，不称已爆火。外部资料只在能实质补足判断时查阅：用户给出页面链接时用可用的只读网页/连接器访问，不用桌面CUA；无法访问就记录并请用户提供证据，不绕过登录限制、不索取凭据。没有必要不扩大成高消耗全网调研。

## 讨论与确认

1. 形成独立初步分析，以“初步判断，待确认”的核心摘要放在分析最前面，提交主要论点/依据/不确定项给用户。
2. 用户尚未补充时，“用户判断与观点”写“尚未提供”，不能代填。已提供则按原意记录，可保留原话与出处日期；不要擅自改写立场。
3. 用户补充后重新核对：哪些结论保留、哪些修改/撤回、哪些不同意，说明证据与理由。不同意见分别呈现，既不无根据附和，也不抹除用户观点。
4. 提交共同总结，分析状态为“待最终确认”。只有明确同意分析结论或具体结论范围才更新为“已确认”。“已保存”、提供截图、同意技术归档、批准Skill安装不等于确认某个案例分析。
5. 用户只确认部分观点时标出已确认范围与仍待确认部分，整体未全部确认不要记为全篇已确认。有分歧则保留，不能虚构共识。

默认允许技术事实和分析草稿先保存；分析依次标为“待用户补充观点／讨论中／待最终确认／已确认”。如果用户要求讨论全部完成才写，遵从该顺序。原始观点保留，不将待讨论草稿当最终共识。

确认后只修改相关分析章节、确认信息及索引状态，保留参数和快照。结论实质变化重新进入待确认；新的投稿量只追加观察，不自动改写结论。记录日期、修改原因和确认范围，不用逐字聊天记录淹没主档案。

## 展示结构与交付

分析章节包含：核心判断摘要、Codex独立初步分析、用户判断与观点、讨论后的确认结论、分歧/替代解释/证据缺口。确认前正式结论位置标“尚未确认”，初步分析照常可读。

技术归档与分析草稿完成后，向用户返回主档案、关键独立判断和真正需要讨论的点，再等待输入，不持续调工具。确认后反馈最终共识与主要修改、双状态和剩余缺口，不称“爆火原因已证实”。
